# ARUS DOMOD — frontend

Интернет-магазин таджикского свадебного костюма: продажа и **прокат** платьев,
украшений и аксессуаров. Фронтенд-MVP, задача которого — показать клиенту
визуальный уровень будущего продукта.

Тексты интерфейса и комментарии в коде — на русском. Названия товаров,
категорий и разделов могут дублироваться на таджикском.

## Команды

```bash
npm run dev        # http://localhost:3000
npm run build      # продакшн-сборка (она же гоняет TypeScript)
npm run typecheck  # tsc --noEmit
npm run lint       # eslint
```

`npm run typecheck` на свежем клоне падает на `LayoutProps`, пока не выполнен
хотя бы один `next build` — типы маршрутов генерируются сборкой в `.next/types`.

## Стек

Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · Tailwind CSS v4.

Состав зависимостей ровно такой, каким его создаёт `create-next-app`. Ни одна
библиотека сверх этого не добавлена и добавляться не должна без явной причины:
анимации, иконки, склейка классов и орнаменты сделаны своими средствами.
Бэкенда, базы, авторизации, оплаты и админки в проекте нет.

# Визуальное направление

ARUS DOMOD выглядит как современный международный дом моды, у которого
таджикское наследие — основа визуального языка, а не декоративная наклейка.
Ориентир — крупные editorial-композиции, сильная типографика, большие
изображения и premium-подача товара.

## Ҳошия — главный приём

Ҳошия — тканая кайма по краю ткани. В интерфейсе это значит:

- секции не просто ставятся друг на друга, а **подшиваются** каймой по краю;
- орнамент живёт **на границах** блоков волосяной линией, а не фоном под текстом;
- чередование светлых и чёрных секций повторяет ритм полос атласа —
  это композиционный приём, а не пользовательская тёмная тема.

## Чего не делаем

- Шаблон «header → баннер → 4 карточки → текст → footer». Композиция должна
  иметь ритм и переходы: смену поверхности, смену плотности, смену масштаба.
- Ковровой орнамент по всему экрану. Не больше одного орнамента на смысловую
  зону экрана.
- Музейную/этнографическую подачу. Национальное работает внутри luxury fashion,
  а не вместо него.
- Градиенты, glassmorphism, декоративные тени, скругления «на всякий случай»,
  анимации ради анимаций.
- Случайные цвета мимо палитры и произвольные `text-[18px]` мимо ролей.

# Design system

Единственный источник правды — `src/styles/tokens.css`. Компоненты используют
**только** семантические токены (`--surface-*`, `--text-*`, `--accent`, …) и
сгенерированные из них Tailwind-утилиты (`bg-page`, `text-ink-secondary`,
`border-hairline`). Сырые ступени палитры (`--madder-700`, `--bone-200`) вне
`tokens.css` не используются — единственное исключение задокументировано в
`src/components/ui/Tag.tsx`.

## Цвет

Палитра выведена из таджикского текстиля, а не подобрана на глаз:

| Семейство | Источник | Роль |
|---|---|---|
| `bone` | небелёный хлопок чакана | фон страницы, светлые поверхности |
| `ink` | плотный чёрный грунт атласа | текст, ночные секции |
| `madder` | марена: красное поле ковра и полосы атласа | акцент, CTA, скидки |
| `zar` | латунь и золотая нить сюзане | декор, плашки, каймы |
| `nil` | индиго ковровой каймы | вспомогательная тёмная поверхность |
| `sabz` | оливково-шалфейные полосы атласа | приглушённый акцент |

Правила контраста, проверенные при подборе: золото — не цвет текста на светлом
фоне (~2.5:1), там оно линия, рамка или подложка с тёмным текстом; на ночной
поверхности акцент переключается с `madder-700` на `madder-400`; главная кнопка
на чёрной секции — `variant="inverse"`, а не красная; ошибка близка к
акцентному красному, поэтому всегда идёт со словом или иконкой.

## Поверхности

Поверхность задаётся атрибутом `data-surface` на секции, а не классами на
каждом элементе:

```tsx
<Section surface="night">   // → data-surface="night"
```

Внутри переключаются **все** семантические токены сразу, поэтому один и тот же
компонент корректно выглядит и на светлой, и на чёрной секции без `dark:`
вариантов. `data-surface="day"` возвращает светлую схему внутри ночной секции.

Глобальной тёмной темы у сайта нет и `prefers-color-scheme` намеренно не
слушается: витрина должна выглядеть одинаково у всех.

## Типографика

Две гарнитуры, обе с полным таджикским набором:

- **Cormorant Garamond** — витринная антиква: display, заголовки, названия товаров.
- **Golos Text** — интерфейс, цены, микро-заголовки.

`subsets` обязаны включать `cyrillic-ext`: буквы **ӯ ҳ ҷ қ ғ ӣ** лежат именно
там. Manrope и Onest этих глифов не содержат вовсе — покрытие проверяется
измерением глифа в браузере, а не по списку subsets.

Каждый текст обязан быть одной из ролей из `src/styles/base.css`:
`t-display-1`, `t-display-2`, `t-h1`, `t-h2`, `t-h3`, `t-lead`, `t-body`,
`t-body-sm`, `t-caption`, `t-label`, `t-label-wide`, `t-price`.
Произвольные размеры и межстрочные в разметке запрещены.

- Заголовки — только антиквой, вес 400: у дома моды нет bold-заголовков.
- CAPS уместен только в `t-label` / `t-label-wide` (трекинг 0.16–0.28em).
- Цены — `t-price`, табличные цифры, иначе колонки карточек «пляшут».

## Ритм и раскладка

- Горизонтальные поля даёт только `<Container>` через текучий `--gutter`
  (20px → 48px); ручные `px-*` на секциях не ставим. Вертикальный ритм —
  `<Section rhythm>`. Ширины: `wide` 1440px, `narrow` 1120px, `text` 68ch.
- Брейкпоинты — Tailwind по умолчанию плюс `xs` 480px и `2xl` 1600px.
  Разработка мобильная-первая.

## Радиусы, границы, тени

- Радиус по умолчанию — **2px** (`rounded-xs`): ткань режут, а не скругляют.
  `rounded-pill` — только чипы фильтров и счётчики в шапке.
- Поверхности разделяет **волосяная линия** `border-hairline`, а не тень.
  Тени — только для всплывающего.

## Изображения

Вся обработка — через `<Media>` (`src/components/ui/Media.tsx`):

- кадр по умолчанию портретный 3:4 (одежда), есть `editorial` 4:5, `tall` 2:3,
  `wide`, `square`, `auto`;
- `sizes` обязателен везде, кроме одиночного hero во всю ширину;
- наезд при наведении — `scale(1.035)` за `--dur-veil`, только внутри `group`;
- `secondary` + `hoverReveal` дают второй кадр, проступающий при наведении.

Внешние хосты — в `images.remotePatterns` (`next.config.ts`), пока пуст.

### Фотографии

Съёмка дома лежит в `фото товаров/` — это исходники, в вёрстку они не идут.
Отобранные кадры подготовлены в `public/photo/`, метаданные — в
`src/lib/photos.ts`.

```
фото товаров/       исходники от клиента, растут по мере съёмок
public/photo/       отобранное: длинная сторона ≤1600px, JPEG q82
src/lib/photos.ts   размеры + blurDataURL, сгенерированный манифест
```

Правила:

- Кадр подключается только через `photo("slug", "описание")`. Alt обязателен.
- `width`/`height` из манифеста нужны, чтобы кадр не прыгал при загрузке,
  `blurDataURL` — чтобы витрина не мигала белым. Руками blur не пишут:
  манифест генерируется вместе с содержимым `public/photo/`.
- У товара до двух кадров: общий план и второй ракурс, проступающий при
  наведении. Если второго нет — ни счётчика, ни миниатюр не рисуем.
- Затемняющие подложки — **служебные, ради читаемости текста**. Декоративных
  затемнений и виньеток в проекте нет.

### Тканая плита (`FabricPlate`) — запасной кадр

Когда фотографии для слота ещё нет, `<Media>` рисует не серый прямоугольник,
а полотно: жаккардовый раппорт из мотива, переплетение нитей и студийный свет.
Вариант `detail` — крупный план абра с растушёванными краями (в абрбандӣ
краска затекает, и жёсткие стыки полос сразу читаются как CSS).

Плита исчезает, как только у слота появляется фотография. Мотив жаккарда
меняется от блока к блоку; каймы ҳошия на плите нет — на каждой плитке она
превращает ткань в обои. Это единственное место (кроме `<Tag>`), где берутся
сырые ступени палитры и мягкий свет: и то и другое изображает фотографию.

## Орнамент

Четыре мотива в `src/styles/ornament.css`, компоненты — в
`src/components/ornament/Ornament.tsx`:

| Мотив | Источник |
|---|---|
| `chorkhona` | ступенчатый ромб крестовой вышивки чакан |
| `dandona` | зубчатая треугольная кайма по краю атласа |
| `mavj` | волна-зигзаг межполосного шва |
| `gul` | розетка сюзане |

Реализованы через CSS `mask`, а не `background-image`: маска красится
`currentColor`, поэтому орнамент сам подхватывает цвет секции и переключается
вместе с день/ночь без второго набора ассетов.

Законы: не больше одного орнамента на смысловую зону экрана; он всегда
монохромный и `aria-hidden`; под основным текстом орнамента не бывает — только
края, разделители и пустые состояния; сила по умолчанию `quiet` (16–20%),
`strong` — точечно.

## Движение

Токены: `--dur-instant|fast|base|slow|veil`, `--ease-quiet|silk|standard`.

- Появление при скролле — только `<Reveal>`: снизу вверх, 18px, без пружин.
- Наезд на фото — `.motion-zoom`, подчёркивание — `.motion-underline`.
- Первый экран — `.motion-enter` и `.motion-veil`: у hero нельзя ждать скролла.
- Панели — `.motion-drawer` и `.motion-fade`: снизу на телефоне, справа на
  широком экране. Закрытие без анимации.
- Больше примитивов движения нет. Новый добавляется в `base.css`, а не
  инлайн-стилями в компоненте.
- Библиотека анимаций (`motion`) намеренно не подключена: всё нужное — reveal,
  наезд, кроссфейд, состояние шапки — это transform и opacity на CSS-переходах.
  Ставить 50 КБ рантайма ради этого нельзя.
- `prefers-reduced-motion` глушит всё в `base.css` — в компонентах эту проверку
  дублировать не нужно.

## Страница образа

`/product/[slug]`. Композиция редакционная: кадры занимают семь колонок из
двенадцати и прокручиваются, колонка с ценой прилипает рядом — подпись к
развороту, а не товарный блок сбоку.

- **Кадры лежат стопкой, а не в карусели.** Второй уходит вправо более узкой
  колонкой, как врезка на развороте. Раскладка одна на все экраны, меняется
  направление: на телефоне это лента со snap-прокруткой. Двух наборов разметки
  быть не должно — браузер декодировал бы скрытые кадры заодно с видимыми.
- **Полноэкранный просмотр** — та же лента на scroll-snap. Активный кадр
  выводится **из позиции прокрутки**, а не наблюдателем пересечений: у
  прокрутки один источник правды, и она не зависит от видимости вкладки.
- Плавная прокрутка галереи глушится при `prefers-reduced-motion`.
- **Ничего пустого не рисуется.** Одно предложение — переключателя нет;
  размеров у изделия не бывает — нет и ряда размеров; один кадр — нет ни
  счётчика, ни миниатюр, ни стрелок. Пустой селектор врёт о товаре не меньше,
  чем выдуманная характеристика.
- Липкая панель телефона появляется, когда основной CTA уехал, и прячется на
  секции `PRODUCT_STORY_ID` — иначе она навсегда закрыла бы низ подвала.
- Раздел после hero говорит о подходе дома, а не о конкретном изделии.

## Корзина, избранное, оформление

`src/lib/cart.ts` и `src/lib/favorites.ts` устроены одинаково: хранилище вне
React, подписка через `useSyncExternalStore`, снимок пересобирается только при
изменении (новый массив на каждый вызов увёл бы React в бесконечный рендер).

Оба переживают перезагрузку через localStorage. **Восстановление идёт при
первой подписке, а не во время рендера** — то есть уже после гидратации: иначе
сервер отдал бы пустое состояние, клиент при первом рендере восстановленное, и
React сообщил бы о расхождении разметки. Данные из хранилища проверяются по
форме (`src/lib/storage.ts`): непрошедшее молча отбрасывается.

**Строки корзины хранят только идентификаторы.** Названия, кадры и цены
страница берёт из репозитория по slug (`useCartProducts`), поэтому второй
копии данных о товаре нет. Покупка и прокат разведены в отдельные группы;
залог показан отдельной строкой и **не входит в итог** — он возвратный.

`/checkout` — прототип: нативная форма, проверка браузером, состояние
«принято» без номера заказа. Оплата — `PaymentPlaceholder`: ни ключей, ни
запросов, ни имитации ответа. Подключение Alif сведётся к замене компонента.

Cart, Favorites и Checkout спокойнее витрины: человек пришёл совершить
действие, а не рассматривать кампанию.
## Каталог

Состояние живёт в одном месте — `CatalogView`. Он собирает `CatalogFilters`,
превращает их в `CatalogQuery` и спрашивает репозиторий; остальные компоненты
каталога презентационные.

- **Флага «идёт загрузка» нет.** Выдача хранится вместе с ключом запроса,
  который её породил (`queryKey`), и устаревание выводится сравнением ключей.
  Флаг, который надо не забыть сбросить, — источник вечных багов.
- **Фасеты решают, что показывать.** `listFacets()` считает каждую грань по
  товарам, прошедшим все прочие фильтры, кроме неё самой: счётчики не
  обнуляются, а грань без значений не рисуется вовсе.
- Категория управляется рядом разделов, а не панелью фильтров: два элемента
  управления одним полем сбивают с толку.
- Раппорт сетки — семь карточек: ряд из четырёх компактных, затем ряд из трёх
  покрупнее. Ряды всегда складываются ровно в 12 колонок, поэтому дырок не
  бывает и `grid-auto-flow: dense` (который ломает порядок сортировки) не
  нужен. **Внутри ряда пропорция кадра одна на всех** — иначе рядом с высокой
  карточкой зияет пустота. Ритм задаётся сменой калибра, а не карточками во
  весь экран: такие приходится листать вслепую.
- На телефоне ритма нет намеренно: две ровные колонки.
- Поиск ищет по названию, имени категории и артикулу. Отдельной страницы
  поиска нет: оверлей открывается поверх текущего экрана.

## Данные о товарах: чего писать нельзя

Фотографии в проекте настоящие — это съёмка ателье. Всё остальное в карточках
синтетическое, и так помечено в `mock-data.ts`.

**Определять характеристики товара по фотографии запрещено.** Нельзя написать,
что на кадре чакан, атлас или адрас; нельзя указать регион, технику вышивки,
состав ткани или срок работы мастера. Это чужое изделие: догадка, записанная
в карточку, становится ложным утверждением о нём — и клиент увидит на своём
сайте неверные сведения о собственных вещах.

Так уже было: карточки получили названия вроде «Чакан «Сурхи Кӯлоб»» и
характеристики «шёлк, золотая нить, Кӯлоб» — всё выведено из снимка и всё
пришлось убрать. Пока данных нет:

- название — номер образа: «Образ 01», `slug: look-01`;
- цены, сроки проката, залоги, размеры и наличие — вымышленные и помечены
  как демонстрационные;
- `attributes` не заполняется вовсе;
- цвет как поле данных не заводится (иначе он выводился бы с фотографии),
  поэтому и фильтра по цвету в каталоге нет.

Нумерация образов — витринная конвенция, а не заглушка: дома моды нумеруют
выходы коллекции. Придут подписи — меняется один файл.

## Шов данных — главное архитектурное решение

Страницы и компоненты **никогда** не импортируют данные товаров напрямую.
Единственная дверь — `catalog()` из `src/lib/catalog`.

```
src/lib/catalog/
  repository.ts       контракт CatalogRepository + реестр
  mock-repository.ts  демо-реализация: фильтры, сортировка, пагинация
  mock-data.ts        единственный файл с конкретными товарами
  index.ts            регистрация источника + catalog()
```

`index.ts` — единственное место, которое знает, что за данными стоит mock.
Переход на реальный API = заменить там импорт на `apiCatalogRepository`.
Ни одна страница и ни один компонент при этом не меняются.

Контракты в `src/types/catalog.ts` учитывают то, что дороже всего чинить
задним числом: деньги — целые **минорные единицы** плюс код валюты (форматирует
`formatMoney()`, float-цен в компонентах нет); цена живёт в `offers[]`, потому
что вещь может и продаваться, и сдаваться; списки всегда `Paginated<T>`;
в маршрутах `slug`, `id` внутренний, а имя категории карточка получает
отдельным пропом — `categorySlug` она не показывает.

## Конвенции компонентов

- Клиентские компоненты — только там, где есть состояние или DOM API.
- `cn()` не разрешает конфликты Tailwind-классов (tailwind-merge не подключён):
  компонент отдаёт базовые классы, вызывающий — только непересекающиеся.
- Интерактив карточка принимает **слотом** (`action` в `ProductCard`).
- У шапки есть `backdrop-filter`, а он создаёт containing block для
  `position: fixed`. Любой полноэкранный оверлей внутри шапки обязан рендериться
  порталом в `document.body` — иначе `inset-0` схлопывается до высоты шапки.

### Зависимости эффектов — по значениям, а не по ссылкам

`listFacets()` возвращает новый объект `{min, max}` при каждом вызове. Мемо по
его идентичности пересчитывался всегда, дальше пересобирался запрос, менялись
зависимости эффекта, эффект снова шёл за данными — и так без конца. Страница
простаивала, а главный поток был занят: **именно отсюда брались «залипающие»
клики**, а не из оверлеев и не из анимаций.

Правила, которые из этого следуют:

- зависимостями эффектов и `useMemo` служат **примитивы** (числа, строки), а не
  объекты и массивы, пришедшие из данных;
- обновление состояния, полученного асинхронно, сверяется с ключом запроса:
  `setData(prev => prev.key === nextKey ? prev : next)` делает цикл
  невозможным структурно, а не по договорённости;
- обработчики, которые уходят в зависимости эффектов (`onClose` и подобные),
  оборачиваются в `useCallback` на месте вызова.

Проверка: временно нарастить счётчик в теле эффекта и открыть страницу. Если
число растёт при бездействии — цикл есть.

### Конфликт утилит одного уровня — самая частая ловушка проекта

Две Tailwind-утилиты одного свойства и одного уровня (`inline-flex` и `hidden`,
`px-7` и `px-0`, `relative` и `absolute`) разрешаются **порядком в
сгенерированном CSS, а не порядком в атрибуте `class`**. `cn(base, "hidden")`
не гарантирует, что победит `hidden`.

Ловушка срабатывала пять раз (display у иконок, поля ghost-кнопки, фон шапки,
подложки в двух секциях). Правило: если у варианта компонента своё значение
свойства, базовая строка это свойство **не задаёт** вообще (см. `iconBox` в
`SiteHeader`, `paddingClass` в `Button`). Нужна другая позиция — заворачивайте
в обёртку. Варианты с разным брейкпоинтом (`hidden sm:inline-flex`) безопасны.

### Шапка

`SiteHeader` — клиентский компонент с двумя состояниями. Список маршрутов с
тёмным первым экраном — `OVERLAY_ROUTES`; на них шапка прозрачная и лежит
внутри кадра, после прокрутки уезжает на высоту бегущей строки, меняет
`data-surface` на `day` и проявляет ҳошия вместо тени. Состояние держится в
React, потому что вместе с фоном обязана переключиться поверхность.

# Состояние проекта

## Сделано

Готов весь путь: главная → каталог → образ → корзина → оформление, плюс
избранное. Маршруты: `/`, `/catalog`, `/catalog/[category]`,
`/product/[slug]` (21 страница пререндерится), `/cart`, `/favorites`,
`/checkout` (прототип).

Главная собрана из семи секций в `src/components/home/`; ритм поверхностей
(ночь → день → ночь → приглушённый день → день → ночь) задаёт
`src/app/page.tsx`, каждая смена подшита ҳошия.

## Следующие фазы

Реальная интеграция Alif, приём заявок, сохранение корзины и избранного между
визитами — всё это требует бэкенда и отдельной постановки.
Они строятся поверх существующих токенов и компонентов. Новый параллельный
визуальный слой не заводим.

Что уже подготовлено: `CatalogQuery` умеет фильтры, фасеты, сортировку и
пагинацию; хранилища корзины и избранного меняются одним файлом каждое;
место оплаты вынесено в отдельный компонент.

## Границы, которые нельзя переходить

Без отдельной постановки в проект не добавляются: бэкенд, база данных,
авторизация, реальная оплата и интеграция Alif, админ-панель.
